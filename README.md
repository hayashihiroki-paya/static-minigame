# static-minigame

学びながら遊べる、静的なミニゲーム集を作るリポジトリです。まずは小さく作り、ゲームのルールを読みやすく保ちます。

## 開発環境

- Node.js 24
- npm

品質チェックに必要な環境を整えます。

    npm ci

ライツアウトのTypeScriptソースをブラウザー向けの静的ファイルへ変換する場合は、次を実行します。

    npm run build

生成物は `dist/games/lights-out/` に置き、ホーム画面から静的ファイルとして開きます。ライツアウト以外のゲームは引き続きソースを直接配信します。

ブラウザーでの確認は、リポジトリのルートでローカルHTTPサーバーを起動します。

    python3 -m http.server 8000

ブラウザーで http://localhost:8000 を開きます。

## 品質チェック

Pull Requestにする前に、次のコマンドを実行します。

    npm run check

このコマンドはJavaScriptの構文、TypeScriptの型検査、自動テストを確認します。ライツアウトの静的ビルドは `npm run build` で確認し、同じチェックとビルドをGitHub Actionsでも実行します。ビルド工程はライツアウトだけに使います。

## GitHubの初回設定

CIの成功をマージの必須条件にするには、GitHubの Settings → Branches で main のブランチ保護ルールを追加し、Pull Request経由の変更と Quality / quality の成功を必須にします。この設定がない場合、CIは結果を表示しますが、失敗した変更のマージを防ぎません。

## 開発の約束

- すべての作業はGitHub Issueで管理します。変更を始める前にIssueを作り、目的と完了条件を記載します。
- Issueには着手時、主な進捗や判断、完了時の作業ログを残します。
- 動作の変更には自動テストを追加します。バグ修正には再発防止テストを追加します。
- 変更はIssueに紐づくPull Requestで提案し、CIが成功してから完了とします。
- AI作業の詳しいルールは AGENTS.md、Issueの入力項目は .github/ISSUE_TEMPLATE/ を参照します。

## ゲームを追加するとき

ゲームの仕様と完了条件をIssueに書きます。各ゲームの実装は src/games/<game-id>/ にまとめ、ルールや状態を扱うロジックには自動テストを用意します。テストにはNode.js組み込みのテストランナーを使います。操作方法、開始・終了条件、やり直し方法も利用者に分かるようにします。

画面を確認するときは、キーボード操作、タッチ操作、狭い画面での表示も確認項目に含めます。

新しいゲームでは、可能な範囲で毎回ひとつ、新しい技術または手法を試します。言語やフレームワークに限らず、描画方法、状態管理、アルゴリズム、テスト手法なども試行の対象にできます。ゲームの目的に合うものを選び、無理に新しい要素を加える必要はありません。

ゲームごとのIssueには、試す技術・手法、選ぶ理由、学びたいこと、変更範囲、確認方法を書きます。一度に試す主な新要素はひとつを目安にし、複数を組み合わせる場合は理由も記録します。既存ゲームを新技術へ移行する作業は、新しいゲームの試行と分けて別Issueで扱います。

試行にあたっても、静的サイトとしての配信、キーボードやタッチでの操作、自動テスト、CIの方針を保ちます。新しい依存関係やビルド工程を導入する場合は必要性をIssueで説明し、ビルドをCIでも確認します。PRまたはIssueの完了ログには、実際に試したこと、分かったこと、問題点や次回に活かすことを日本語で残します。
